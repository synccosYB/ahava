# Ahava Medical Center - Time & Attendance System

## Overview
This project is an employee time tracking and attendance management system for Ahava Medical Center. Its core purpose is to streamline clock-in/out, manage attendance, handle time-off requests, and provide robust administrative tools for HR and management. Key capabilities include a tablet-based kiosk for shared device clock-ins, comprehensive PTO management, and a flexible policy engine. The system aims to improve operational efficiency, ensure accurate payroll data, and provide clear oversight of employee attendance and leave, ultimately enhancing business vision and market potential for medical center time management.

## System Architecture
The system is built with an Express.js backend (TypeScript), a React frontend (Vite, TanStack Query, Wouter, Shadcn/ui), and a PostgreSQL database with Drizzle ORM. Authentication is handled by Replit Auth (OpenID Connect) using session-based sessions and JWTs for API access.

**Technical Implementations:**
- **Role-Based Access Control (RBAC):** Granular permissions via roles, user overrides, and access scopes (division/company, location, department). Enforced by middleware. **Convention:** every key passed to `requirePermission(...)` in `server/routes.ts` MUST exist in `PERMISSION_KEYS` in `server/seed.ts` and be granted to at least one system role. The drift guard `server/__tests__/permissionDrift.test.ts` enforces this and will fail loudly if a route gates on a key the seed catalog doesn't define (regression for task #210, where `company.create`/`edit`/`delete` were dropped from the catalog but still gated routes — which silently 403'd every non–Super Admin).
- **Migration Safety & Deployment:** Migrations run at boot via `server/migrate.ts` (idempotent, replay-safe, recorded in `_migration_log`) BEFORE the HTTP server listens, so a bad migration fails fast. After migrations, `verifySchema()` runs an automated **drift guardrail**: the expected tables/columns are derived directly from the Drizzle models in `shared/schema.ts` (`server/schemaDrift.ts`, via `getTableConfig`) — NOT a hand-maintained list — and the boot throws loudly if the DB is missing any model table/column (i.e. a migration is missing). **Convention:** edit a model → `npx drizzle-kit generate` and commit the migration, or the app won't boot. Same check runs standalone as `npx tsx scripts/check-schema-drift.ts` (CI/release gate) and is tested by `server/__tests__/schemaDrift.test.ts`. Full release/rollback runbook, feature-flag policy, and schema-change checklist live in `docs/deployment-safety.md`.
- **Policy Engine:** Dynamic, hierarchical rule resolution for attendance, PTO, payroll, approvals, alerts, and kiosk behaviors. Policies are defined with JSON rules.
- **Time & Attendance:** Manages `punch_logs`, `attendance_exceptions` (with approval workflows), and `hoursWorked` computation.
- **Unified Pay Calculation Engine:** `server/payrollEngine.ts` is the SINGLE authoritative source for turning hours-worked into regular/overtime/double-time hours and into pay dollars. EVERY consumer routes through it (clock-out enforcement, timesheet, reports, payroll batch create/CSV/summary, reconciliation verification) so the numbers never drift across surfaces. Core pure fns: `splitDailyHours`, `computeGrossPay`, `summarizeDailyHours`, `buildPayCalcPolicy`/`resolvePayCalcPolicy`. **Conventions:** (1) OT is split PER DAY then summed — never `rangeTotal - daysWorked*8` (that let long/short days net and under-reported OT). (2) Multipliers/thresholds are NEVER hard-coded — OT pays at the payroll policy `overtimeMultiplier` (default 1.5x), double-time at `doubleTimeMultiplier` (default 2.0x), OT threshold from attendance `otThresholdDaily` (default 8), DT threshold from payroll `doubleTimeThresholdDaily` (default 12); `holidayOtExclusion` (pto policy) keeps a holiday's hours all-regular; on/off toggles are treated as `true` unless explicitly `false`. (3) **Historical stability via snapshot:** when a payroll batch is created the FULL resolved policy is FROZEN onto each `payroll_batch_records` row — numeric knobs + hourly rate (`ot_threshold_daily`, `double_time_threshold_daily`, `overtime_multiplier`, `double_time_multiplier`, `hourly_rate`, `double_time_hours`, `policy_version` — migration `0055_payroll_double_time_snapshot`) AND the on/off toggles + the holiday determination (`auto_calculate_ot`, `overtime_enabled`, `double_time_enabled`, `holiday_ot_exclusion`, `is_holiday` — migration `0056_payroll_policy_toggle_snapshot`). CSV export, summary, and reconciliation PREFER these snapshot columns and only fall back to the live profile/policy + current schedule for legacy rows, so editing a policy (or an employee's schedule) never changes already-exported historical dollars. **If you add a new pay-affecting input to `splitDailyHours`, snapshot it too or historical verifications will drift.**
- **PTO Management:** Tracks `time_off_requests` (time-off vs. cashout) and `time_off_balances`. PTO accrual/caps/carryover/expiration are configured as `pto` policies in the **unified policy engine** (`policies` + `policy_rules`), resolved per-employee via `storage.getEmployeePtoPolicy → getEffectivePolicy`. PTO cash-outs integrated with payroll exports. **Single-source guarantee:** every PTO read surface (employee `/api/time-off/my-balance`, team `/api/time-off/balance`, request enrichment on `/api/time-off/pending`, and payroll `POST /api/payroll/exports`) derives its numbers from `computeTimeOffBalanceDetailed`, which reads only the engine — pinned by `server/__tests__/ptoEngineParity.test.ts` (annual + per_hours_worked w/ cap, carryover cap, anniversary tier delta, and a static guard that no balance-math method reads the legacy table).
- **LEGACY — `pto_policies` table (DORMANT):** Post-consolidation, NO balance/accrual number is read from `pto_policies`. It survives only as (a) a defensive last-resort fallback in `getEmployeePtoPolicy`/`getDefaultPtoPolicy` when the engine resolves nothing, and (b) the legacy `GET /api/pto-policies` CRUD endpoints. It is **documented as legacy, not dropped**, because two FKs still reference it: `employee_pto_settings.pto_policy_id` and `pto_anniversary_adjustments.pto_policy_id`. **Known bug:** the latter FK is stale — the anniversary job (`server/services/ptoAnniversary.ts`) writes the engine's unified `policies.id` into `pto_anniversary_adjustments.pto_policy_id`, violating the FK, so anniversary adjustments silently fail to persist in prod (per-employee error swallowed). Fixing it (drop those FKs + retire the table) would change PTO behavior, so it is filed as a follow-up rather than done here.
- **Audit Logging:** Robust system for capturing sensitive operations.
- **Alerts:** System alerts for various attendance violations with acknowledgement and resolution workflows.
- **Policy Enforcement:** Real-time enforcement at clock-in/out (grace periods, rounding, break requirements, auto clock-out). PTO enforcement for advance notice and blackout dates. Background job for stale punches.
- **Real-time Updates:** WebSocket integration (`/ws`) for live attendance updates.
- **Performance & Cost Hardening:**
    - **Server:** `helmet()`, `compression()`, rate limiting, response cache (for read-heavy GETs), cooldown for expensive POSTs, slow-request logging, optimized DB pooling, `jobs` table for background tasks.
    - **Client:** `cachedFetch` with in-memory TTL cache and single-flight, `use-debounce` hook for search inputs, relaxed refetch intervals, strictly user-triggered reports.
    - **Cache invalidation (stale-data guard):** Both cache layers are kept fresh automatically so users never see "I saved it but nothing changed." **Server:** the global `requestCacheInvalidator()` middleware (registered first in `registerRoutes`, defined in `server/lib/requestCache.ts`) busts the entire request cache via `invalidateRequestCache()` on any successful (2xx/3xx) mutating request, synchronously before the response flushes. Mutation routes do NOT need to invalidate by hand — the legacy `invalidateUserCache()` helper now just delegates to the shared invalidator. **Client:** `apiRequest` in `client/src/lib/queryClient.ts` calls `invalidateCachedFetch()` after every successful non-GET request, so the in-memory `cachedFetch` cache clears in lockstep with `queryClient.invalidateQueries`. Failed mutations leave both caches intact (nothing changed). Regression coverage: `server/__tests__/requestCacheInvalidation.test.ts`.
- **Biometric Kiosk (Phase 1: Face Recognition):**
    - Feature-flagged (master switch + per-modality `faceEnabled`); both default OFF. Stores only encrypted 128-dim face descriptors (Float32 → JSON number array) client-side. No images or raw camera data leave the browser. Compute happens in `client/src/lib/face-api.ts` (`@vladmandic/face-api`, models lazy-loaded from CDN; URL overridable via `VITE_FACE_MODELS_URL`).
    - **Schema:** migrations `0021_biometrics` (7 tables: settings, legal profiles + scopes, consents, templates, attempts, supervisor overrides) plus additive `0022_biometric_settings_extras` (per-modality / lockout knobs: `face_enabled`, `liveness_required`, `min/max_samples_per_enrollment`, `max_attempts_before_lockout`, `lockout_duration_minutes`, `supervisor_override_requires_pin`, `match_timeout_ms`). All `IF NOT EXISTS`, replay-safe.
    - **Encryption:** AES-256-GCM (`iv ‖ authTag ‖ ciphertext`, base64) with `BIOMETRIC_ENCRYPTION_KEY` (32-byte base64). Required in prod (server throws on startup); dev falls back to a random ephemeral key and surfaces a banner in the admin Settings tab. Each row stores `encryption_key_version` for future rotation.
    - **Legal Profiles & BIPA:** Per-tenant profiles with consent text + retention window, scoped via `biometric_legal_profile_scopes` (location > company > default fallback). Editing consent text auto-bumps `consent_version` and forces re-acceptance.
    - **Tiered Confidence:** Euclidean distance → confidence in [0,1]; three thresholds (auto-approve / review / reject). Passive liveness check is a frame-difference signal — explicitly NOT anti-spoof grade and labelled as such; admins can disable.
    - **Kiosk-only device trust:** `/api/kiosk/face/*` are public but require `X-Kiosk-Device-Id` header resolving to an active `kiosk_devices` row (read from `localStorage.kioskDeviceId` set during admin pairing). Without it, kiosk simply hides the "Use Face" button and falls back to PIN.
    - **Supervisor Override:** After N consecutive failures (configurable), manager/admin PIN + reason → `biometric_supervisor_overrides` + audit log → normal Confirm/Success flow.
    - **Retention & Legal Hold:** Daily `biometric-retention` job (`server/services/biometricRetention.ts`) deletes templates by inactivity, consent revocation, or termination. `legal_hold` flag on a consent row pauses deletion (HR investigations). Admins can fire a sweep on demand from Settings.
    - **Audit Trail:** Every consent/enrollment/deletion/setting change/override hits `audit_logs` via `writeAuditLog`. Decrypt events are logged WITHOUT payload.
    - **Permissions & UI:** `biometrics.manage` permission (seeded onto HR Admin role). Admin page `/biometrics` with tabs Dashboard / Enrollments / Attempts / Overrides / Legal Profiles / Settings. Sidebar entry `link-nav-biometrics` with `ScanFace` icon. Employee `/profile` renders `<BiometricLoginCard/>` only when feature is on; gracefully renders nothing otherwise.
    - **Admin-initiated enrollment:** The Enrollments tab lets an admin start a face enrollment for an employee from the admin's own device, reusing `<FaceCapture/>`. It is strictly consent-gated: the "Start enrollment" action only appears for employees with an active consent on file, and `POST /api/biometrics/users/:id/enroll` (gated by `biometrics.manage`) re-checks `getActiveBiometricConsent` server-side and returns 412 otherwise — admins can never enroll a non-consented employee (BIPA). The template is attributed to the acting admin (`enrolledByUserId`) and writes a `biometric.admin.enrolled` audit entry. The enrollment summary returns a canonical row shape (`userName`/`userEmail`/`templateId`/`enrolledAt`/`hasActiveConsent`); the status badge distinguishes Enrolled / "Consent received · Not enrolled" / Revoked / No consent. Legal-hold placeholder consents leave `revoked_by` null (it FKs to `users.id`, so a sentinel like "system" caused a 400) and are excluded from real-consent status calculations.
    - **Tests:** `server/__tests__/biometric.test.ts` covers encryption round-trip, tamper detection, and matcher correctness — run with `npx tsx server/__tests__/biometric.test.ts`.

**Feature Specifications:**
- **Employee Work Schedules:** Per-employee weekly schedule configuration with clock-in/out warnings.
- **Kiosk System:** Public `/kiosk` route for PIN/name search clock-in/out.
- **Dashboards:** Employee dashboard (clock status, hours, PTO) and Manager/Admin dashboards (team/division stats, approval queues).
- **Admin Pages:** Dedicated sections for Employees, Locations & Departments, Time Clock Rules, PTO & Leave, Alerts & Exceptions, Payroll Prep, Payroll Documents, Reports, Permissions, Roles, Kiosks, Audit Log.
- **Payroll Documents:** Employee-facing and admin pages for managing pay stubs and tax forms.
- **Punch Correction:** Forms for employee punch correction and manager exception queue with side-by-side comparisons. 90-day correction request counts (time_correction + missing_punch) are surfaced to employees in the correction dialog (`text-self-correction-count`), to managers in incoming exception rows (`CorrectionCountBadge`), and on the manager Employee Profile (Employment tab, `field-correction-counts`). Threshold of 5+ within 90 days is emphasized as "Frequent corrections" via shared constants in `shared/correctionCounts.ts`. Once a correction request is approved, denied, or cancelled, that date is locked on My Attendance — the row shows the verdict badge instead of "Request Fix". The employee can send one "Ask to reopen" message per resolved exception (`POST /api/attendance/exceptions/:id/reopen-request`), surfaced to managers/admins under a Reopen Requests section on Requests & Approvals (`GET /api/attendance/exceptions/reopen-pending`). Admins grant or decline (`POST /api/attendance/exceptions/:id/reopen-decide`); a granted reopen unlocks the date for one new correction submission and is consumed when used. All transitions write to `audit_logs` (`exception.reopen.requested|granted|declined|consumed`).
- **Per-Employee Timesheet:** Day-by-day attendance view available in two places — embedded in the Employee Profile "History / Audit" tab (above the audit log, with date range picker and totals row) and as a dedicated "Employee Timesheet" tab on the Reports page with CSV export. Backed by `GET /api/attendance/timesheet/:employeeId?startDate&endDate` (self/team/admin scoped) and `GET /api/timesheet/eligible-employees` (admin/manager-scoped employee picker). Empty days render as `—`, approved PTO days surface as `PTO`, days exceeding the daily OT threshold are flagged as `Overtime`. Aggregate totals (`totalHours`, `overtimeHours`, `daysWorked`) are computed via the shared helper `computeAttendanceTotals` in `server/timesheetService.ts`, which is also used by `/api/reports/generate` so the per-employee timesheet's totals row matches the time report row exactly. Shared frontend component `EmployeeTimesheetTable` lives in `client/src/components/employee-timesheet.tsx` and is consumed by both the Employee Profile and Reports pages.
- **Employee Audit History:** Server-side, employee-scoped audit feed at `GET /api/audit-logs/employee/:userId?limit&offset` (returns `{ logs, total }`). Authorization mirrors the timesheet endpoint (self/team/admin). The Employee Profile "History / Audit" tab no longer fetches a global `limit=1000` slice — it now requests the page size it wants and grows by 25 rows per `Show more` click, so older entries are never dropped.
- **HR Onboarding & Employee Management:** Multi-step "Add Employee" dialog, admin password reset (choice of temp password or email reset link via /api/users/:id/reset-password), self-service forgot-password flow at /forgot-password and /reset-password backed by `server/services/email.ts` (Resend, activates when `RESEND_API_KEY` is set) + `server/services/passwordReset.ts` (1hr single-use sha256-hashed tokens stored in `password_reset_tokens`), forced password change, document management (W-9, I-9, etc., stored in Replit Object Storage), onboarding checklist.
- **Bulk Division Assignment:** Frontend multi-select with bulk action bar; backend endpoint for assigning users to divisions.
- **Policy Builder Wizard:** Reusable 4-step wizard for creating/editing policies with type selection, rule configuration, assignments, and review. Payroll bonus rules (Day-of-Week and Early-Arrival) are guarded against day overlaps both client-side (Add disabled, inline conflict messages, per-row errors, blocked Next/Save) and server-side (PUT/POST/PATCH /api/policies endpoints reject 400 on overlap). Shared overlap helpers live in `shared/policyOverlap.ts`. **Assignment targets** (Company/Location/Department/Employee/Role) load from a single consolidated endpoint `GET /api/policy-assignment-targets`, gated by the SAME `requireRole("admin")` as policy management itself — NOT the per-resource view permissions (`company.view`/`locations.view`/`departments.view`/`users.view`). **Why:** the shared list endpoints each require a granular view permission, so any policy-management role whose RBAC role lacked one returned a 403 → empty array → that wizard "Level" was silently disabled, blocking the whole Target dropdown. Routing the wizard through one admin-gated picker keeps target loading consistent with the gate that already lets a user open the wizard. The wizard no longer disables empty Levels — they stay selectable and show a contextual message ("No <level> options are available."), with a global empty-state when no real targets of any kind exist.
- **Visual Workflow Builder:** Drag-and-drop builder using `@xyflow/react` for creating node-based workflows (Trigger, Condition, Approval, Action, Notification). Backend `workflowEngine.ts` executes active workflows.
