## 1. Project Overview & Stack

Build a multi-location employee time clock and PTO management system. This is an admin-side platform where management controls employees, punch rules, PTO rules, missing punch approvals, alerts, and payroll-prep exports.

This is **not** a payroll processing system. It prepares clean, validated data for export to a payroll provider.

**Stack:**
- Frontend: React + TypeScript + Tailwind + ShadCN UI
- Backend: Node.js + Express
- Database: PostgreSQL
- ORM: Drizzle
- Auth: JWT + role-based permissions
- Realtime: WebSockets (live attendance board)

## 2. Product Requirements (PRD)

### 2.1 Objective

Allow administrators to:
- Manage employees across multiple locations
- Enforce clock-in / clock-out rules
- Configure PTO and sick leave policies
- Handle missing punch requests with an approval workflow
- Monitor alerts and exceptions
- Prepare payroll-ready time summaries (export only — no processing)

### 2.2 Scope

**Phase 1 — Included:**
- Admin authentication and roles
- Multi-location company structure
- Employee management
- Time punch tracking
- Missing punch request and approval workflow
- PTO and sick policy engine
- PTO request workflow
- Alerts and exception tracking
- Payroll prep (export and tracking only)
- Reports
- Audit logs

**Phase 2+ (excluded from initial build):**
- Mobile app
- Geofencing
- Biometric devices
- Messaging system
- Advanced scheduling
- Payroll processing integrations

### 2.3 Admin Panel Navigation

Sidebar sections (in order):
- Dashboard
- Employees
- Locations
- Time Clock Rules
- PTO & Leave
- Requests & Approvals
- Alerts & Exceptions
- Payroll Prep
- Reports
- Rules & Controls

### 2.4 Dashboard

**KPI Cards (top row — 6 cards):**
- Employees Clocked In Now
- Missing Clock Outs
- PTO Requests Pending
- Missed Punch Requests Pending
- Overtime Alerts Today
- Total Hours Worked Today

**Main content:**
- Live attendance table: Employee, Location, Clock-In Time, Current Hours, Status (On Time / Late / OT Risk)
- Exceptions panel: missing punches, late arrivals, unauthorized punches
- Approval queue panel (right side): PTO requests, punch corrections, time edits

**Filters:** Location, Department, Date, Employee Type, Active/Inactive

### 2.5 Employee Module

**List columns:** Employee ID, Name, Status, Location, Department, Pay Type, PTO Eligible, Last Punch, Active/Inactive

**Employee Profile — 8 tabs:**
1. Basic Info — name, ID, phone, email, address, emergency contact, photo
2. Employment — hire date, status, type (FT/PT/temp/contractor/per diem), exempt/non-exempt, department, location, manager, payroll group
3. Pay Setup — pay type (hourly/weekly salary/daily salary), rates, voluntary pay toggle, overtime eligible, holiday pay eligible
4. Time Clock Settings — allowed punch methods, geofence toggle, rounding rule override, grace period override, auto meal deduction, shift enforcement
5. PTO/Leave — eligibility toggles, accrual profile assignment, waiting period, yearly cap, carryover, manual balance adjustment
6. Schedule — assigned shift template, recurring work days, break windows
7. Documents — signed policies, handbook acknowledgment
8. History/Audit — punches, edits, approvals, PTO changes, admin actions

### 2.6 Requests & Approvals Module

**Request types handled:**
- PTO requests
- Missing punch requests
- Manual time corrections

**Missing punch fields (employee submits):**
- Date
- Time
- Type: clock-in or clock-out
- Reason

Employee cannot directly edit punch logs. Admin approval creates the corrected record.

**PTO request review shows:** employee, location, requested dates, hours requested, available balance, eligibility check, overlapping shift check, note. Actions: Approve / Deny / Partially Approve.

### 2.7 Payroll Prep

- Admin selects date range
- System validates: no missing punches, no unapproved edits
- Export generates CSV: Employee, Regular Hours, OT Hours, PTO Hours, Issues flag
- Period is marked as exported/sent with timestamp and user
- Re-exporting same range: warning shown, not blocked
- Punch corrected after export: flagged as "adjustment required — review next payroll"
- Export blocked if unresolved missing punches exist in date range

### 2.8 Reports

- Attendance — daily, late arrivals, absences, early departures
- Time — total hours by employee/location, overtime breakdown
- PTO — accrued, used, liability, carryover
- Missing Punches — per employee, filterable by week / month / year
- Exceptions — repeated late, manual edits, suspicious activity
- Audit — who changed what, when, old/new value, approvals

All reports have date range filters and CSV export.

## 3. User Roles & Permissions

### 3.1 Roles

| Role | Access |
|---|---|
| Super Admin | Full system access |
| Company Admin | Manage employees, PTO, rules |
| HR Admin | PTO and employee management |
| Payroll Admin | Payroll prep and exports only |
| Location Manager | Assigned location only |
| Department Manager | Assigned department only |
| Supervisor | View team, approve requests |
| Employee | Self-service only |
| Kiosk Device | Non-human device role |

### 3.2 Permission Keys

All ~30 permission keys seeded into the `permissions` table at setup:

```
attendance.view_self         attendance.view_team
attendance.view_all          attendance.edit
attendance.approve_corrections  attendance.manage_rules
pto.request                  pto.view_self
pto.view_team                pto.view_all
pto.approve                  pto.manage_policies
payroll.export               payroll.mark_sent
payroll.view_batches         users.view
users.create                 users.edit
users.deactivate             roles.manage
settings.manage              reports.view
kiosk.manage                 alerts.manage
audit.view
```

### 3.3 Permission Resolution

1. Load role-level permissions from `role_permissions`
2. Apply user-level overrides from `user_permission_overrides` (always wins)
3. Enforce scope — users only see data within their `user_access_scopes`

### 3.4 Required Middleware (3 functions)

```
requirePermission(permissionKey)
requireScopedAccess(module, scopeResolver)
getEffectivePolicy(companyId, userId, policyType)
```

`requirePermission` must be applied server-side on every API route. Frontend permission gates are supplementary only.

### 3.5 Permission Matrix UI (Milestone 8)

Grid with rows = modules, columns = actions (view / edit / approve / export), checkboxes per role. Admin can create, edit, and duplicate roles from this screen.

## 4. Business Rules (Non-Negotiable)

All values must be admin-configurable via the rules engine. Nothing in this section may be hardcoded.

### Attendance
- Employees cannot edit punch logs directly under any circumstance
- Employees submit attendance_exceptions with: date, time, type (clock-in or clock-out), reason
- Admin or manager approval creates or updates the corrected punch_log record
- Every approval writes an audit_logs entry
- Double clock-in must be prevented
- Clock-out without an active clock-in must be rejected

### PTO
- PTO settings are company-wide defaults with per-employee overrides
- PTO balance is not visible to employees — admin only
- All PTO behavior must read from the active policy via `getEffectivePolicy`

### Sick Leave
- Default: 1 hour earned per 30 hours worked
- Default yearly cap: 40 hours
- Both accrual rate and cap are configurable per policy
- Admin can override both per individual employee

### Holidays
- Holidays are unpaid by default
- Paid holidays can be enabled per policy (toggle)
- If paid, hours may optionally deduct from PTO bank (separate toggle)
- Holiday hours must never count toward overtime thresholds

### Payroll
- Exported date ranges are marked sent and tracked
- Re-exporting same range triggers a warning
- Punch corrected after export: auto-generate payroll_adjustment record, flag batch as "adjustment_required"
- Export blocked if unresolved missing punches exist in range
- Lock/reopen behavior reads from payroll policy

### Alerts
- Auto-generate for: missing clock-out, late clock-in, overtime threshold, unauthorized punch location, repeated issues
- Each alert type: enabled/disabled toggle, notify roles, escalation behavior — all configurable

UI label: **Rules & Controls** (not "Settings").

Lowest level always wins:
1. Employee (highest priority)

## 6. Database Schema

### Company Structure

**companies** — id, name, legalName, timezone, isActive, createdAt, updatedAt

**locations** — id, companyId, name, code, address1, city, state, zip, timezone, isActive, createdAt, updatedAt

**departments** — id, companyId, locationId, name, managerUserId, isActive, createdAt, updatedAt

### Users & Access Control

**users** — id, companyId (extend existing), email, passwordHash (extend existing), firstName, lastName, isActive, createdAt

**roles** — id, companyId (nullable for system roles), name, description, isSystem (bool), isActive, createdAt, updatedAt

**permissions** — id, key (unique), module, description, createdAt

**role_permissions** — id, roleId, permissionId, createdAt — unique(roleId, permissionId)

**user_roles** — id, userId, roleId, createdAt — unique(userId, roleId)

**user_permission_overrides** — id, userId, permissionId, allowed (bool), reason, createdBy, createdAt, updatedAt — unique(userId, permissionId)

**user_access_scopes** — id, userId, companyId, locationId (nullable), departmentId (nullable), scopeType: company/location/department, createdAt

### Employment

**user_employment_profiles** — id, userId, companyId, locationId, departmentId, employeeNumber, employmentType (full_time/part_time/contractor/per_diem), payType (hourly/salary_weekly/salary_daily), hourlyRate, weeklySalary, dailySalary, overtimeEligible (bool), holidayPayEnabled (bool), voluntaryPayEnabled (bool), isActive, hireDate, terminationDate, createdAt, updatedAt

### Attendance

**punch_logs** — id, employeeId, workDate, clockIn (timestamp), clockOut (timestamp), source (web/mobile/kiosk/admin/system), approved (bool), hoursWorked (numeric), createdAt

**attendance_exceptions** — id, companyId, userId, attendanceRecordId (nullable), type (missing_punch/manual_edit_request/no_show/late_in/early_out/overtime_exception), status (open/pending_approval/approved/denied/resolved), requestedClockIn (timestamp, nullable), requestedClockOut (timestamp, nullable), reason, submittedBy, reviewedBy, reviewComment, createdAt, updatedAt

**audit_logs** — id, companyId, actorUserId, targetType, targetId, action, oldValue (jsonb), newValue (jsonb), context (jsonb), ipAddress, userAgent, createdAt

### PTO

**pto_policies** — id, companyId, name, accrualType (per_hours_worked/weekly/monthly/annual_lump_sum), accrualRate, hoursPerAccrualUnit, yearlyCapHours, carryoverCapHours, waitingPeriodDays, holidaysPaid (bool), paidHolidayDeductsFromPto (bool), holidayExcludedFromOvertime (bool), sickRuleEnabled (bool), sickHoursPerWorkedHours, sickYearlyCapHours, isDefault (bool), createdAt, updatedAt

**employee_pto_settings** — id, employeeId (unique), policyId, overridePtoBalanceHours, overrideSickBalanceHours, createdAt

**pto_requests** — id, employeeId, startDate, endDate, hoursRequested, note, status (pending/approved/denied/cancelled), approvedByUserId, createdAt

### Rules Engine

**policy_types** — id, key (unique), name — seeded: attendance, pto, payroll, approvals, alerts, kiosk

**policies** — id, companyId, policyTypeId, name, description, status (draft/active/archived), version (int), isDefault (bool), createdBy, createdAt, updatedAt

**policy_rules** — id, policyId, rules (jsonb), createdAt, updatedAt

**policy_assignments** — id, companyId, policyId, assignmentLevel (company/location/department/employee), locationId (nullable), departmentId (nullable), userId (nullable), effectiveFrom (date), effectiveTo (date), priority (int), createdAt, updatedAt

### Payroll

**payroll_exports** — id, companyId, locationId (nullable), name, periodStart, periodEnd, exportedAt, exportedBy, status (draft/exported/locked/reopened), notes, createdAt, updatedAt

**payroll_batch_records** — id, payrollBatchId, attendanceRecordId, timeOffRequestId, userId, workDate, isPaid (bool), wasModifiedAfterExport (bool), modificationFlagAt, createdAt

**payroll_adjustments** — id, employeeId, payrollExportId, adjustmentDate, reason, createdAt

### Alerts

**alerts** — id, companyId, locationId, userId, alertType, severity (info/warning/critical), title, message, metadata (jsonb), status (open/acknowledged/resolved), triggeredAt, resolvedAt, resolvedBy

### Kiosk

**kiosk_devices** — id, companyId, locationId, name, deviceCode (unique), isActive (bool), lastSeenAt, createdAt, updatedAt

**kiosk_device_rules** — id, kioskDeviceId, allowedLocationId (nullable), requirePin (bool), allowNameSearch (bool), restrictToDepartmentId (nullable), isActive, updatedAt

## 9. Milestones

Build in this exact sequence. Do not build UI for any module before its backend service is stable and tested. Extend existing working modules — do not rebuild what functions correctly.

### Milestone 1 — Foundation: Schema, Auth, RBAC
**Relevant files:** `shared/schema.ts`, `server/routes.ts:9-21`, `server/storage.ts:27-84`, `server/index.ts`, `server/seed.ts`, `server/replit_integrations/auth/replitAuth.ts`, `drizzle.config.ts`, `shared/models/auth.ts`

**Done looks like:**
- New tables created: companies, locations, roles, permissions, role_permissions, user_roles, user_permission_overrides, user_access_scopes
- Existing `users` table extended with `companyId` and `passwordHash` (backward compatible with existing auth)
- Existing `departments` table extended with `companyId` and `locationId` foreign keys
- All ~30 permission keys seeded into `permissions`
- 9 system roles seeded with default `role_permissions` mappings
- `requirePermission(key)` middleware works: resolves role permissions + user overrides, returns 403 if missing
- `requireScopedAccess(module, scopeResolver)` middleware works
- Auth middleware accepts JWT or existing session (dual-mode during transition)
- Existing routes continue to function during migration
- Seed script populates permissions, roles, role_permissions, policy_types
- IStorage interface updated with methods for new tables

**Tasks:**
1. Create Drizzle schema files for all new access control tables — follow column definitions in Section 6 exactly
2. Extend `users` table: add `companyId` FK and `passwordHash` column; update auth model types
3. Extend `departments` table: add `companyId` and `locationId` FKs
4. Write seed scripts for all permission keys, 9 system roles, and their role_permissions mappings
5. Implement `requirePermission` middleware (role permissions + user overrides)
6. Implement `requireScopedAccess` middleware (company/location/department filtering)
7. Add JWT generation on login; create combined auth middleware (JWT or session)

## 10. Developer Rules

These are non-negotiable. Review before writing any code.

**1. No hardcoded business logic.**
Grace periods, PTO caps, sick accrual rates, holiday behavior, approval chains, and payroll locking must all resolve through `getEffectivePolicy`. If admin might ever want to change it, it must be configurable.

**2. Backend is the source of truth.**
Frontend may hide pages and buttons based on permissions, but every API endpoint must independently enforce permissions server-side. Frontend-only access control is not acceptable.

**3. Scope every query.**
Users must only see data within their assigned company, location, or department. A location manager must never see another location's data. Scoped filtering applies to every list and detail endpoint.

**4. Employees cannot edit punch logs directly.**
Employees submit attendance_exceptions. Admin or manager approval creates the corrected punch_log record. There is no direct edit path for employees under any condition.

**5. Audit everything sensitive.**
Any change to rules, permissions, payroll status, punch records, PTO approvals, or employee data must write an audit_logs row: actor, action, entity type, entity ID, old value, new value, timestamp.

**6. Extend, do not replace.**
If existing attendance, PTO, kiosk, and reporting flows are already working, refactor them to read from the rules engine rather than rebuilding from scratch.

**7. Build backend before UI.**
No admin screen is built before its corresponding backend service and validation logic is stable and tested.

**8. getEffectivePolicy is the architectural center.**
Every module that reads a business rule calls this function. It is built in Milestone 5 and nothing should bypass it after that point.
